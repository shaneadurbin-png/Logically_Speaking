## House rules (do not drift)

1. **Readers identify files by content**, never by name: a header fingerprint per layout (`app/onrent_vendors.js` LAYOUTS, `PurchasePro.REQUIRED`, `JCTD.HEADER`, ...). `app/sniff.js` tries them in order.
2. **Refuse rather than guess**: `C.UnknownFormat` / `C.NotForThisPage` / `C.NeedsDecision` (asks the person, e.g. an as-of date) with a plain-English reason. A number the file does not give is `null`, never 0. Lines that cannot be counted are shown and counted as "no monthly figure".
3. **Money in integer cents**, `C.roundHalfUp`; basis points for tax and markup.
4. **Every rule lives twice**: JS module (UMD, runs in browser and Node) and SQL (views in `supabase/migrations/`), held together by generated parity tests. The demo adapter `app/db_local.js` mirrors every SQL view the page reads.
5. **Actuals are never edited**: uploads are recorded through RPCs that recount what the page sent (`finalize_upload`), forbid triggers on the line tables, superseding with a reason. Settings tables are audited.
6. **Viewers never see names or employee numbers.** Names live only in `employees` (editors).
7. **Decisions in `docs/LEDGER.md`** (L-nn) and open questions (Q-nn). Add one for every rule you add.
8. **Public repo:** no real exports, no server names, no credentials, no people's names in fixtures or docs.

## Rules learned from the real data this week (already built, see LEDGER L-29..L-32)

- Sunbelt's all-jobs export has no Quantity: a line with a serial number is one unit; a bulk line shows its rate and is not counted. Its date is Date Rented + Number of Days on Rent (every line must agree). EquipmentShare's On Rent Report: the same date rule (Rental Start Date + Total Days on Rent); the portal writes the literal "null" for empty cells.
- Purchase Pro's Tbl_PO has no primary key. A PO with no job never refuses (quotes are left out, live orders wait). A PO number can sit on two orders, an OrderID on a quote and the order it became, and one order came twice: nothing refuses, every row is kept, every order whose number is on more than one row waits for a decision, and a decision carries across exports by number AND OrderID (`app.purchase_docs_resolved`, migration 0014).
- A month with no on-rent report by its last day takes the first report after it, within seven days (`rentals_model.snapshotForMonth`, migration 0015). The package is pulled a day or two into the next month.
- Prefix defaults (FB5 → Laborer journeyman ...) are a setting (`prefix_classes`, 0013), editable on Settings › Employees.
- The weekly cost workbook's `Labor` sheet is the labor history (L-33, 0016): loaded once, each row priced at the cost the workbook gave it (`cost_given_cents`, `price_source = 'given'`) with the class it carried (`class_given`); the `Labor Audit` sheet's PTO rows are held. Jobs seen on time sheets are catalogued on Record (L-34). The weekly HH2 files add to the baseline.
- The per-project review Shane wants (his dashboard HTML of week ending 9/20): a campus/project and week-ending filter; Labor: total labor cost, REG/OT/DT hours, headcount, cost by cost code name (top 12, the selected week), labor by employee (editors), hours by week for the last four weeks by trade; Rentals: monthly and weekly (÷ 4.33) burdened cost, items on rent, equipment by description, cost by vendor, cost by category (top 8); POs: committed this week, last week, MTD, YTD, the PO table, committed by week ending for four weeks. Build it as the Report page's by-week view (plan item 11 above), one job or all.
- Shane's Purchase Pro FRONT END (.accdb) was read here with mdbtools (`apt-get install mdbtools`; `mdb-tables`, `mdb-export`, `mdb-queries`): it holds no PO data (Tbl_PO and Tbl_PODetail are links to the back end), but its saved queries settle three things. (1) The full column lists of Tbl_PO and Tbl_PODetail are exactly the ones in the plan above (the local copies `OrderF_CopyT` / `OrderFDetail_CopyT` carry them). (2) Purchase Pro's Sage import (`PO_Import_C` / `PO_Import_CI`) writes one commitment record per PO (key `<PO>_01`) and one commitment ITEM per line keyed `<PO>_02_<Tbl_PODetail.ID>`, carrying job, extra, cost code, category (Cost_Type), tax group, qty (Material: Qty; Rental: Qty × NoOfPeriods; LS: 0), unit price, UOM, extended cost, rental start and end, and the line ID in column 23: so a PO line maps to Sage's commitment item by the line's own ID, not by amount. (3) Rental orders are rows of the same two tables (`RentalWorkingDataQ`: OrdType <> Material and RentalStatus <> Off Rent). The same tool reads the BACK END too: a copy of `PO_Mission_Critical_BE.accdb` dropped in this environment yields the full-detail CSV without the PowerShell exporter (`mdb-export` of the two tables, joined on OrderID), which is the fastest way to test the full-detail reader on real data. Never commit either file.
- TimberScan (Sage AP approval) has a "Job Cost Invoices Inquiry" grid with Export To Excel: invoices in flight with vendor, invoice, type, and distribution (commitment, job, cost code, category, amount). Once a sample lands, a reader for it closes the gap open = committed − posted − in TimberScan and ties invoices to POs by commitment number.

## Gotchas

- The smoke needs `BASE=file://<repo>`; without it it looks for a server on :8794.
- A `<form>` inside `<tr>` is parsed by the browser with the form-pointer trick; the page relies on it (`form.emp`, `form.decide`): `data-*` on the form, not on children.
- `create or replace view` only when columns are appended at the end; otherwise drop and recreate the dependents (see 0011).
- A new enum value cannot be used in the migration that adds it (0010 then 0011).
- Commit messages: plain English, what and why; no model names in repo artifacts.
